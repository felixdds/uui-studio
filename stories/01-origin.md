# 一个牙医为什么想做跨平台开发工具

简体中文 · [English](en/01-origin.md)

我是一名牙医，不是职业程序员。我用过 Delphi 7，喜欢它的可视化开发体验，但没有接受过系统的软件工程训练，也不懂 Rust。UUI Studio 的想法，却在我真正有能力实现它之前，留在心里很多年。

## 2014 年留下的一个问题

2014 年，HTML5 的发展让我产生了一个念头：不同系统上的应用，有那么多相似的界面概念，为什么要重复开发？按钮、输入框、面板、菜单、布局、事件和数据展示，很多共同部分能不能统一描述，把真正的平台差异留给底层处理？

我希望有一套工具，既保留类似 Delphi 的可视化体验，又能支持跨平台应用。当时我缺少实现能力，这个想法就保留了十二年。

到了 2026 年，我先尝试让 Codex 做一些自动化工作，包括从文字生成视频、再发布到 YouTube。这让我重新考虑：能不能让 AI 帮我把那个跨平台 UI 的想法做出来？于是，我们开始了 UUI Studio。

## 我带来的首先是一种习惯

在长期牙科临床工作中，我习惯追问：为什么一定要这样操作？哪些步骤真正有必要？有没有办法让接受治疗的人少承担一些不必要的负担？

安全、临床效果、患者体验和患者满意，才是我关心的目标。速度可能随着方法改进而提高，但它只是副产品。需要复杂处理时，就保留必要的复杂性；能够减少不必要的干预时，也不必只为了沿用习惯而保留它。

我把这种习惯带到了软件开发里。在诊所，我关心接受治疗的人；在 UUI Studio，我关心使用工具的开发者，以及他们所创造应用的最终用户。

因此，我可以要求 Codex 删除一个不必要的组件，也可以为了让用户少点一次鼠标，让它增加一些代码。我经常开玩笑：“为了让用户少点一次鼠标，我宁愿让 Codex 多写十行代码。反正不是我写，哈哈。”

这两种要求的方向不同，判断标准却相同：结果和体验有没有变好？简单与复杂都是手段。

## 想法终于有了可以检验的形式

我负责需求、架构规则、方向和实际体验判断；Codex 负责实现代码、编译、调试和技术检查。我没有亲自编写这个项目的实现代码，但我需要判断它是否符合我要解决的问题。

很多时候，我的起点只是一句：“这个能不能做到？”接下来才是尝试、检查、修改，有时甚至推翻重来。UDM 和 UUI Studio，就是在这个过程中逐步形成的。

十二年前，我只有一个想法。现在，我终于可以面对一个实际的软件，继续问：“为什么不能做得更好一点？”
