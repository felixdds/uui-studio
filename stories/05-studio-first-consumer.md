# 开发工具先遵守自己的规则

我不希望 Studio 成为凌驾于 UDM 之上的特殊存在。它自身的主要界面，也应该使用这套组件和布局规则。

## 第一个消费者

Studio 使用 Panel、Button、SplitButton、主题、语言以及布局机制，与用户开发的应用遵循相同的模型。这意味着，我们在开发 Studio 时，也持续使用和检验 UDM。

如果一个组件或规则在实际工具界面中不好用，Studio 自己就可能先遇到。解决它时，我希望改进的是共享机制，让应用也能从中受益。

我不想维护两套彼此脱离的体系：一套专门让 Studio 工作，另一套再交给用户。开发工具应该首先遵守自己制定的应用模型。

## Studio 本身就是持续使用模型的应用

对我来说，Studio 不仅是用来编辑应用的工具，它自身也是一个持续使用 UDM 的复杂应用。面板怎样布局、属性怎样编辑、主题怎样切换，这些机制要在日常开发中真正工作，不能只在一次演示中看起来正常。

这使 Studio 成为重要的架构检验者。如果为了完成它的界面，总得绕开 UDM、另写特殊逻辑，我就需要追问：是模型缺少必要能力，还是实现没有遵守已有规则？我希望我们通过改进共同机制解决问题，而不是让工具自己享有一套用户应用用不到的捷径。

同时，Studio 的需求不能覆盖所有应用。现有的十个可编辑示例提供了其他使用场景；以后需要更多例子时，也可以继续增加。但从十个增加到一百个，本身并不证明架构成熟。更有意义的是，例子能否覆盖不同的数据、布局、交互和平台条件，暴露问题，并检验同一套规则是否仍然成立。

## 共享机制 保持独立

但遵循同一套机制，不代表必须共享同一个状态。

Studio 和应用可以选择不同的主题，也可以使用不同的语言。Studio 是英文界面，应用可以是中文界面。英文 Studio 中的 AI Workspace，也可以接受中文指令、处理中文内容并用中文反馈。

应用的运行环境与 Studio 保持隔离。这种独立性，是为了让编辑工具和被编辑的应用各自正常工作。这里讨论的是运行环境和状态的边界，不把它扩大成已经完成全部安全隔离验证的结论。

## 翻译也需要知道源文是否变化

语言系统通过英文源文本的 Hash 追踪变化，帮助识别哪些翻译需要更新，以及哪些源文已经删除、翻译条目却仍然存在。

我发现功能已经具备，但列表还能更容易理解，于是要求把条目分为三组：

- 源文已经删除的条目，可以清理。
- 源文变化后需要更新的条目。
- 已更新的条目，仍允许继续编辑。

Codex 在实现和检查时，还发现旧翻译可能从发行资源重新进入系统的问题，于是继续修复。这次没有增加新组件，只是让已有机制更合理。

对我来说，这与 Studio 首先使用 UDM 是相通的：通过真正使用发现问题，再把改进放回合适的位置。
